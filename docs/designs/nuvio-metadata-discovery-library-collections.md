## Problem Statement

Fasti has durable source-neutral Records and metadata-claim storage, but the active product stops short of the promised metadata and Nuvio experience. The trusted Desktop host performs real Google Books and TMDB searches. The browser host exposes truthful setup-required placeholders. Search is local filtering, Discover is a one-shot candidate finder, Library is a bounded Record view, Collections are not a source-neutral domain entity, and full Nuvio state synchronization is not composed.

The programme must make those capabilities real without changing the central rule: a Fasti Record has stable local identity. Provider identifiers, metadata, ratings, grouping choices, and export identifiers remain evidence or projections.

## What Makes This Useful

- A person can find a title from configured providers without first knowing the provider namespace.
- Search candidates do not silently become Library state.
- Metadata disagreement remains inspectable at field level.
- Library state and Collection membership remain local and usable when a provider is unavailable.
- Nuvio can consume safe catalog and metadata projections without becoming Fasti's identity or storage model.
- Anime grouping and IMDb, MAL, or Kitsu preference can change an export projection without moving history.

## Constraints

- Preserve the existing UI and mature incomplete behavior incrementally.
- Keep Search, Discover, Library, Collections, metadata, ratings, and synchronization as separate capabilities.
- Reuse the current provider-security boundary: resolve once, authorize every address, pin the client, disable proxies and redirects, bound requests, and keep credentials in headers or native secret storage.
- Never expose provider credentials, bearer tokens, or capability tokens in browser storage, logs, manifest URLs, or provider URLs.
- Consume the authentication programme's sessions, grants, OAuth clients, device flow, and final vault. Do not reopen or edit its canonical plan.
- Use Tabler-first composition, persistent status, visible focus, 44px targets, reduced motion, stable layouts, and resumable review.
- Keep memory, package, migration, conformance, accessibility, and performance gates from the repository Definition of Done.
- Implement Kaptain interoperability against user-supplied Nuvio documents. Do not bundle or copy Kaptain source or assets while its licence is absent.
- Fetch MDBList data for the authorized account and purpose. Do not create a public redistribution mirror or share account-scoped cache entries.

## Premises

1. Search finds candidates. Discover presents governed catalog rails. Library presents local user-owned state. Collections organize Records and catalog sources. Metadata enriches fields.
2. One external provider ID must never become the identity of a Fasti Record.
3. The current generic models are useful foundations, but new production composition roots are required.
4. A standard Stremio-compatible surface can publish non-sensitive read-only catalog and metadata projections. It does not provide Library, progress, watched, or Collection writes.
5. Nuvio's private Supabase RPCs are not a Fasti integration boundary. M11 defines a versioned public Fasti provider contract and implements matching upstream Nuvio clients.
6. MDBList ratings, catalogs/lists, and account synchronization are separate grants and capabilities.
7. Nuvio anime-ID preference is a grouping/export policy, not canonical identity.
8. Nuvio Desktop preserves unknown Collection JSON fields, while NuvioTV typed round trips can discard them. Fasti must preserve unknown fields and warn about lossy downstream edits.

## Approaches Considered

### A. Extend the existing paths directly

Add providers and UI behavior to the existing Tauri modules, then consolidate shared contracts later. This produces early visible progress but prolongs browser/Desktop divergence and duplicates provider policy.

### B. Shared contracts and complete vertical slices — selected

Establish shared registries, domain boundaries, durable state, and generated contracts first. Deliver each capability as a complete vertical slice through store, application, API/native host, UI, contracts, tests, documentation, and evidence.

### C. Nuvio compatibility layer first

Build Nuvio catalog and state adapters around current Records before completing shared Search, Library, and Collections models. This can produce an early Nuvio demonstration but risks a parallel data model that must later be replaced.

## Recommended Approach

Use approach B. The first branch is docs-only M0 from exact `origin/dev@adbdef3038786b0efb2ec615bce080e3eaa9361f`. It freezes the source ledger, ownership boundaries, dependency graph, threat model, migration order, capability-ID allocation, PR graph, acceptance matrix, and Definition of Done.

## Ownership Decisions

| State | Owner and scope | Rule |
| --- | --- | --- |
| Record identity and external assertions | Workspace | Provider-independent and shared by every profile. |
| Provider metadata claims and public rating claims | Workspace | Immutable evidence with provider, route, locale, retrieval time, expiry, digest, and lifecycle. |
| Metadata projection policy and field overrides | Profile | A profile can choose presentation without changing shared evidence or another profile's view. |
| Provider application credentials | Node/data root | One governed `CredentialReference`; no browser copy and no second vault. |
| Provider account OAuth grants | Connection plus profile grant | The Connection owns the remote account; explicit grants map it to profiles and capabilities. |
| Library saved/progress/watched/rating/note state | Profile | Each state is separate and cannot be inferred from Collection membership. |
| `Collection` and ordered membership | Profile | Local source-neutral organization of Records. |
| `CollectionSourceBinding` | Profile Collection | A live external catalog reference; it is not copied membership until materialized. |
| `CollectionPackDescriptor` | Immutable registry/cache | Version, source, digest, author, licence, requirements, and rollback metadata. |
| Raw Nuvio Collection document | Profile import/export envelope | Preserve the complete JSON and unknown extension fields separately from normalized Fasti entities. |
| Discover rail definitions | Profile or administrator-published workspace template | Rails bind sources but never become Library state. |

Archive v3 includes profile projection policy, overrides, Library state, Collections, pack receipts, raw Nuvio documents, connections without secrets, cursors, and tombstones. Restore reconnects `CredentialReference` values only when the destination vault proves the same node identity.

## Collection Vocabulary

- `Collection`: a Fasti profile-owned entity with ordered Record membership.
- `CollectionFolder`: presentation grouping inside one Collection.
- `CollectionSourceBinding`: a configured live source such as TMDB Discover, MDBList list, or add-on catalog.
- `CollectionPackDescriptor`: immutable installation metadata for a versioned set of Collection definitions.
- `CollectionPackReceipt`: profile-owned install, merge, replacement, and rollback evidence.
- `NuvioCollectionEnvelope`: lossless raw import/export document with normalized references and an extension bag.

Conversion is explicit. Importing a Nuvio envelope creates a dry-run plan. Installing a pack creates Fasti entities and a receipt. Materializing a source binding copies selected candidates into membership. None of these operations silently replace the raw source document.

## Search and Identity Contract

`SearchCandidate` contains an opaque query-scoped candidate ID, source ID, exact source identifiers, media grain, normalized title/year, source cursor, provenance, and one evidence class: `exact_identifier`, `provider_exact`, `likely_duplicate`, or `unresolved`. Numeric similarity is diagnostic evidence, never merge authority.

Candidate grouping retains every source candidate and identifier. Conflicting exact identifiers create an ambiguity group. Search never attaches an identifier or merges Records. Keyset cursors bind the query digest, enabled-source digest, stable source order, provider cursor, and final candidate tuple so pages cannot be replayed against another query.

The create/attach action re-fetches the selected candidate through its exact governed route, revalidates its identifiers, and commits the Record, identifier assertions, initial claims, and action receipt in one SQLite writer transaction. Network calls never run inside that transaction. Title/year-only matches can open review but cannot attach identity automatically.

## Metadata Lifecycle

Field keys are extensible namespaced values grouped into artwork, basic information, release data, credits, companies, networks, episodes, recommendations, collections, trailers, watch providers, and ratings. Each claim records the provider, source namespace/value, locale, region, fetch time, expiry, provider version, evidence digest, and lifecycle status.

Projection order is profile override, fresh preferred provider and locale, compatible fresh fallback, last-known-good stale claim, then empty. Profile language falls back to original language and then English only when policy allows. A provider switch changes projection and routing, never Record identity or Chronicle state.

Cache caps are: search 2 minutes fresh and 10 minutes stale-on-error; Discover/catalog 15 minutes fresh, 15 minutes stale-while-refreshing, and 24 hours stale-on-error; metadata claims 24 hours fresh, 12 hours stale-while-refreshing, and 7 days stale-on-error; positive identity routes 7 days fresh and 30 days stale-on-error; negative identity routes 15 minutes with no stale reuse. Provider headers may shorten but not extend these caps.

Empty responses do not retract prior claims. Explicit upstream deletion or licence revocation marks affected claims `revoked` and recomputes projection. Refresh failure marks status and preserves last-known-good. Cache identity includes provider, safe configuration digest, route, grain, namespace/value, locale, region, field group, settings fingerprint, credential-reference version, and schema version. Raw secrets never enter cache keys.

The freshness table governs fetch-response reuse, not deletion of durable evidence. A claim older than the seven-day stale-on-error response window remains stored as historical evidence. Projection can continue to show it only as visibly `stale` last-known-good when the profile permits stale display; it is never returned as a fresh provider response. An explicit upstream retraction appends a lifecycle event that supersedes the original immutable claim. It does not mutate or erase the original evidence row. A removed field stops projecting after the retraction event unless a profile override or another compatible claim wins.

## MDBList Data Classification

- Public aggregate provider scores are workspace metadata claims only when the MDBList account and current terms permit that use. Their cache is partitioned by provider credential reference, capability, route, and terms revision.
- A profile's own MDBList rating is profile Library state, not a public aggregate claim.
- MDBList watchlist, watched history, collections, playback, and account lists are Connection-owned remote state exposed only through an explicit profile grant.
- Account-derived state is encrypted or referenced through the approved vault, excluded from public Stremio projections, excluded from other profiles, and included in archive v3 only as profile-scoped state or reconnect metadata according to the provider's export terms.
- Public catalog publication can reference only a separately approved redistributable source. Account-scoped MDBList responses remain private Fasti/Nuvio provider responses and are never copied into a public catalog cache.

## Nuvio Publication and Synchronization Security

The standard Stremio-compatible `/manifest.json`, `/catalog`, and `/meta` surface publishes only administrator- or profile-approved non-sensitive projections. It has no streams and no user-state writes. Public catalogs use opaque non-sequential IDs, explicit allowlists, bounded pages, rate limits, cache partitions per published descriptor, and CORS required by the Stremio protocol. Revocation removes the descriptor and purges its cache.

Private Library, progress, watched, rating, and Collection state uses the new Fasti provider contract, not standard Stremio URLs. Nuvio pairs through Authorization Code with PKCE or Device Authorization from the authentication programme, stores a revocable native credential, and sends it in an authorization header. The contract provides capability discovery, snapshot, ordered delta, mutation, deletion tombstones, acknowledgement, cursor recovery, idempotency keys, profile grants, conflict receipts, and diagnostics.

The upstream Nuvio Desktop and NuvioTV changes add a Fasti tracking/provider client against that contract. They do not use service-role credentials, raw passwords, manifest query tokens, or direct database access. Fasti applies the existing resolve-once/all-address authorization and proxy-free/redirect-free client rules to every remote source; inbound provider endpoints enforce grant, profile, origin where applicable, rate, payload, and replay boundaries.

### Synchronization semantics

- A cursor is scoped to one Fasti workspace, profile, connection, capability set, and contract revision. It is opaque to Nuvio.
- Fasti assigns the monotonic sequence inside the same transaction that commits each profile-state change or tombstone. Wall clocks are evidence only and never determine ordering.
- Authority is per field: Fasti-owned Library state is authoritative for Fasti mutations; a Nuvio mutation is accepted only under its granted capability and becomes a normal Fasti change with a receipt. Metadata providers cannot write Library state.
- Explicit deletion creates a tombstone and dominates an older update. A later update must cite the last acknowledged revision and deliberately recreate the state.
- Concurrent writes use compare-and-set revisions. Non-overlapping fields merge. Same-field revision conflicts retain both submitted evidence, leave the last committed value active, and return a conflict receipt requiring deterministic retry or user resolution.
- Idempotency keys bind client, profile, capability, operation, and payload digest. Receipts are retained for at least the maximum offline retry window of 30 days; reuse with a different digest fails closed.
- An acknowledgement is durable only after the client's cursor is stored. Nuvio advances its local cursor only after its local outbox and projection commit atomically.
- The Nuvio client commits a local state change and its immutable operation journal entry in one local transaction. The dispatch outbox is a derived queue of unacknowledged journal entries, not the sole copy of an operation. If the outbox is lost, it is rebuilt from the journal and durable acknowledgements. If a cursor expires, the client requests a bounded snapshot at a named sequence, reconciles by stable state IDs and revisions, reapplies unacknowledged journal entries by idempotency key, then resumes deltas after that sequence. Physical loss of both the local database and its backup is reported as unrecoverable local data loss; no protocol can reconstruct operations that were never sent.

## Migration and Rollback

M0 performs no schema change. At each production slice, fetch current `dev`, inspect the migration ledger and active auth ownership, then allocate the next unclaimed version. Migration files have one writer and merge before dependent branches start. Every migration is transactional, restart-safe, idempotently detected, foreign-key checked, and paired with upgrade fixtures from the oldest supported archive.

Before a storage migration, Fasti creates or verifies a compatible backup receipt. Rollback restores the previous application plus its compatible backup; destructive down-migrations are not used. Archive schema advances to v3 before new profile-owned state ships. Interrupted-migration and restore-after-upgrade tests are mandatory. A changed `dev` head invalidates prior migration and exact-head evidence.

- Library state and Collection membership survive provider outages and metadata preference changes.

- Nuvio catalog/meta passes pinned Desktop `ab498c9`, NuvioTV `7c3baa1`, and Stremio protocol fixtures with no secrets in URLs.
- Write synchronization proves idempotent replay, ordered deltas, deletion tombstones, cursor expiry/recovery, conflict receipts, bounded retry, offline outbox restart, revocation, and profile isolation with real upstream client events.
- UI passes WCAG 2.2 AA, 320 CSS-pixel reflow, 200% zoom, keyboard/focus/forced-colors/reduced-motion checks, Axe, Playwright, and manual screen-reader evidence.

## Reproducible Performance Evidence

M0 records the current exact-head baseline before new runtime code. M12 compares the merged result against it with the existing `scripts/bench-envelope.sh`, `benchmarks/b1`, and `xtask` receipt validators.

- Qualifying idle evidence runs on Linux x86_64 and aarch64 under cgroup v2, one vCPU, zero swap, and the 192 MiB aggregate process-tree ceiling.
- Each architecture uses the governed 600-second warm-up and 900-second route-less idle window with one-second samples and the existing 500 ms lateness rejection.
- The idle profile starts the exact release daemon with its production schema and no route, then enforces both the 64 MiB target and 192 MiB ceiling.
- The normal profile uses the 10,000-Record dataset and runs five requests per second across local Search, Library, Collections, metadata projection, and one bounded background refresh for 15 minutes after warm-up; it enforces the 96 MiB target and 192 MiB ceiling.
- The heavy profile concurrently executes four deterministic provider searches, a 100-result page projection, a 4 MiB/3,059-source pack dry run, a 100-item Nuvio snapshot page, metadata refresh, and cache eviction for 15 minutes after warm-up; it enforces the 160 MiB target and 192 MiB ceiling.
- `scripts/bench-envelope.sh --target idle|normal|heavy` records each target and rejects any sample or cgroup peak above that profile's cap. OOM, swap use, missed samples, early exit, route leakage in idle, or a missing process-tree member fails the receipt.
- Native/Tauri comparison uses at least five independent clean-tree runs; receipts retain exact artifacts, OS image, CPU governor, runtime, process tree, raw samples, minimum/median/maximum, and worst peak.
- Functional latency uses a deterministic 10,000-Record dataset containing every supported grain, 20% unresolved identities, 30% multi-provider claims, 10 Collections per profile, and 100-member/1,000-member Collection cases.
- Cold-cache and warm-cache scenarios run separately. Remote orchestration uses four deterministic provider stubs at fixed 50 ms and 250 ms response latency, one partial failure, one 429, and one cancellation case. No live provider latency is used for the product overhead verdict.
- Each scenario runs five process-isolated repetitions with 30 measured requests after warm-up. The receipt reports p50/p95/p99 and maximum. Every repetition must stay under the memory ceiling; the aggregate p95 must meet the latency target. A regression over 10% from the recorded baseline requires investigation even when the absolute target passes.
