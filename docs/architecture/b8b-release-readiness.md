# Milestone B8b Public Release Readiness Architecture

This document defines what "public release readiness" means for Fasti, which of its nine required streams are machine-checkable today, and exactly where each one is deliberately deferred to B8's own explicit release action.

---

## 1. Scope and dependency

B8b's scope, unchanged from `docs/handoffs/FASTI_EXTERNAL_HARNESS_CONTEXT_SAVE_2026-08-24.md`:

- signed artifacts
- SBOM
- provenance and attestations
- update and rollback path
- final security review
- final accessibility and design review
- final release QA
- release notes and support guidance
- explicit publishing authorization

B8b sits downstream of B8a, B4, and B6 (`B8a → B6 → B8b`, per the capability-ledger dependency chain). Two of the nine streams cannot legitimately close before their upstream body exists:

- **Final accessibility and design review** requires a rendered UI to review. B4 (the Svelte/Tauri UI Workbench) has not been built in this source tree yet. `cargo xtask test milestone --body B8b` therefore requires `design_review.status == Pass`, not `NotApplicable` — a strict requirement that is intentionally unsatisfiable until B4 ships. This is fail-closed by design, not a gap to work around.
- **Explicit publishing authorization** requires a human-approval gate B8b can prepare but not activate: creating the GitHub Environment and its required reviewers is a repo-settings action, not a file change (see §11 and §13).

## 2. Non-publishing boundary

`scripts/check-no-publish.sh` is a real, enforced CI gate (the `B0 repository truth` job, run on every push to `dev`/`release`). It greps every file under `.github/workflows/` and `scripts/` — including comments — for a forbidden-pattern regex that blocks, among others: any Docker/OCI push, `gh release`, the `attest-build-provenance` action, `npm`/`pnpm`/`yarn`/`cargo publish`, `git push`, `gh pr merge/ready/close/edit`, and any `permissions:` line granting `write` on any key.

The rule this implies for every deliverable below: **prepare the mechanism, never execute the publish.** Concretely:

- Docker steps use `docker build` and `docker image save`, never `push` or `--push`.
- Provenance is generated by a plain script, never the `attest-build-provenance` action.
- `cargo cyclonedx` and `cargo deny check` are not `cargo publish` and do not match the forbidden pattern.
- No new CI job adds a `permissions:` block. In particular, the OIDC token a real keyless-cosign step would need (`id-token: write`) is not added here — that belongs to B8's own release workflow.
- `actions/upload-artifact` is safe and already used elsewhere in this repo's CI (`ci.yml`'s `low-hardware-envelope` and `review-source-snapshot` jobs) — it stores artifacts privately to repository collaborators, not a public registry or release.
- This document is not scanned by `check-no-publish.sh` (only `.github/workflows/` and `scripts/` are), so it can and does describe the deferred publish/sign steps in full below.

## 3. Signed artifacts

**Deferred**: real signing. Fasti's chosen mechanism is Sigstore/cosign **keyless** signing — no long-lived private key is generated or stored. At B8 release time, `cosign sign --yes <image-ref>` signs the artifact using a short-lived certificate tied to the release workflow's GitHub OIDC identity, and the signature is recorded in Sigstore's public Rekor transparency log. That log write is itself a publish action, which is exactly why real signing cannot happen before B8: cosign also needs a resolvable registry digest to attach a signature to, and no image is pushed to any registry before B8 either.

**Buildable now**: a per-architecture checksums manifest over the artifacts that already exist without publishing — the native `fastid`/`fasti` binaries and the OCI image's content digest (via `docker image save`, not `push`). This is exactly the byte content a future `cosign sign`/`cosign attest` step signs over. The manifest is self-verified (`sha256sum -c`) in the same CI job, so a stale or hand-edited manifest fails the job instead of silently uploading something wrong.

## 4. SBOM

CycloneDX 1.6 JSON, generated by `cargo-cyclonedx` for the Rust workspace (and separately for the isolated `benchmarks/b1/tauri-shell/src-tauri` lockfile) and `cyclonedx-npm` for the retained JS/pnpm packages. Each output is sanity-checked (`bomFormat == "CycloneDX"` and at least one component) before upload, so a misconfigured tool run fails loudly rather than uploading an empty file that looks complete. Uploaded via `actions/upload-artifact`; never submitted to any public SBOM registry (no OSS Index, no Dependency-Track).

`cyclonedx-npm` shells out to `npm ls`, which disagrees with pnpm's (correct) refusal to flatten a transitive package's own devDependencies into `node_modules`. The CI step runs with `--ignore-npm-errors`, verified locally to still resolve hundreds of real components rather than silently dropping data.

## 5. Provenance and attestations

A plain script (`scripts/generate-provenance.mjs`) emits an in-toto/SLSA-shaped provenance **statement**: subject artifact digests, the exact commit and tree the artifacts were built from (`git rev-parse HEAD` / `HEAD^{tree}`), and the workflow/run identity from `$GITHUB_*` environment variables. It never signs or submits the statement anywhere — it is CI-artifact evidence only, consumed by the B8b milestone manifest.

Nothing in `xtask/src/evidence.rs` builds a provenance statement today. The closest existing material is that file's internal `current_source_binding`/`current_ci_binding`/`current_runner_binding` helpers, whose field values this script mirrors independently — a deliberate, minimal duplication of a handful of `git`/environment reads, not logic worth factoring into the `xtask` binary, since this runs as a CI-step script rather than compiled Rust. Its `source` block uses this repo's own `git_commit`/`git_tree` snake_case field naming (not in-toto/SLSA's own casing conventions, since `source` is a custom addition to the statement, not part of either spec) so the same `ensure_receipt_source` helper `xtask` already uses for every other receipt can validate it too.

## 6. Update and rollback path

No auto-updater exists or is planned for B8b. Rollback is a documented manual procedure: see `docs/operations/rollback-runbook.md`. Both the OCI and native procedures conclude by re-running the existing `scripts/smoke-oci.sh` / `scripts/smoke-native.sh` gates — "rollback succeeded" is defined as "the same smoke gate a fresh deploy has to pass, passes again," reusing the existing bar rather than inventing new rollback-specific verification.

## 7. Final security review

Two gates, both re-run at release time and captured as B8b evidence:

- `cargo-audit` (already running weekly in `security.yml`) for known vulnerability advisories.
- `cargo-deny` (new: `deny.toml` at the workspace root) for license compliance and dependency hygiene — an allowlist consistent with the AGPL-3.0-or-later workspace license and `NOTICE`'s dual-licensing note, a ban on wildcard version requirements, and denial of unknown/yanked sources.

"Final" means both are green against the exact tagged commit, not merely that they passed at some point in `dev`'s history.

`deny.toml`'s check runs against the main workspace lockfile as a blocking gate (clean today, mutation-verified: temporarily removing a currently-used license from the allowlist correctly fails the check). It also runs report-only against the isolated Tauri benchmark shell's lockfile, which carries 13 pre-existing "unmaintained" advisories (GTK3 bindings, `proc-macro-error`, the `unic-*` family) inherited from Tauri's Linux GTK3/webkit2gtk binding stack, with no safe upgrade available upstream. Blanket-ignoring 13 findings to force that check green would be a real judgment call about acceptable risk, not a config detail — left for a maintainer to decide, not decided here.

## 8. Final accessibility and design review

No rendered UI exists in this source tree yet — B4 is a later, currently-absent body (`docs/capability-ledger.md`). This section is therefore a roll-up checklist that will reuse the existing accessibility mechanism defined in `docs/architecture/b4-ui-quality-harness.md` (`@axe-core/playwright`, WCAG 2.1 A/AA, the state-permutation matrix for focus rings, touch targets, contrast, and reduced motion) once B4 ships — not new accessibility infrastructure built here.

Unlike B1 (permanently headless, `design_review.status == NotApplicable` is the correct, permanent answer), B8b's `design_review.status` must read `Pass`. By the time B8b is legitimately closed, B4 sits upstream of it in the dependency graph and has already closed. Until then, `cargo xtask test milestone --body B8b` fails here, correctly.

## 9. Final release QA

Defined as: `cargo xtask test pr` + `cargo xtask test deep` (both already exist) + the new B8b-specific checks (`cargo-deny`, checksums, SBOM, and provenance scripts all exit 0) + a manual QA sign-off receipt, following the same `fasti.qa-review.v1` shape B1 already uses, bound as the `b8b-qa` evidence entry. All of it is captured into one manifest by `cargo xtask test milestone --body B8b`.

## 10. Release notes and support guidance

`scripts/generate-release-notes.mjs` extracts one tagged version's section from `CHANGELOG.md` (Keep a Changelog format, already the repo's convention) into a standalone file — it reads and writes local files only. `SUPPORT.md` (which already exists) gains a "Supported Releases" section pointing at the generated release notes and the rollback runbook.

## 11. Explicit publishing authorization

A GitHub Environment named `production-release`, configured with required reviewers, is the human-approval gate. `release.yml` gains a final `publish` job, `needs:` on every other job in the workflow, gated on `environment: production-release` and only triggered on version tags. Its single step is inert by construction — it runs no build, package-manager, git, or container command of any kind, so it cannot trip `check-no-publish.sh` even after a careless future edit adds more to it. It exists to prove the approval-gate mechanism is wired, not to do anything yet.

**This gate is not actually enforced until a repository admin creates the `production-release` Environment and adds required reviewers in GitHub's Settings → Environments UI.** That is explicitly out of scope for this milestone's file changes (see §13).

## 12. `xtask` wiring

`cargo xtask test milestone --body B8b` is the deterministic B8b software gate, added alongside the existing B1 implementation in `xtask/src/evidence.rs` and `xtask/src/main.rs`. It requires a passing B8a manifest to exist first (fail-closed — B8a's own evidence formalization is a separate, prerequisite body, out of scope here) and then verifies:

| Stream | Machine-checkable by the B8b manifest today | Notes |
|---|---|---|
| Signed artifacts | Partially — checksums entries verified | Real signing/Rekor submission stays out of scope by design |
| SBOM | Yes | Files exist, non-empty, CycloneDX-shaped |
| Provenance/attestations | Yes | Statement exists, source-bound |
| Update/rollback path | No | Doc-only, checked by `check-doc-links.mjs`, not manifest evidence |
| Final security review | Yes | `cargo-deny` receipt bound as evidence, source-bound |
| Final accessibility/design review | No — blocked | `design_review.status` cannot legitimately read `Pass` until B4 ships |
| Final release QA | Yes | `qa.status == Pass` requires a human-authored receipt, machine-verified shape |
| Release notes/support guidance | Yes | Release-notes file exists and is non-empty for the tag |
| Explicit publishing authorization | No | The Environment's approval gate is a GitHub-side mechanism, not manifest-introspectable |

All B8b evidence lives under one evidence root, `target/fasti-evidence/b8b/`, deliberately kept separate from B1's `target/fasti-receipts/` and `target/fasti-evidence/qa/` directories — sharing either would mean B1's own evidence files (present from a prior gate run in the same environment) show up as unbound files and fail B8b's inventory check. B8b's own QA receipt therefore lives at `target/fasti-evidence/b8b/qa/b8b-qa.json`, not the shared `qa/` directory B1 uses.

## 13. Known gaps and out-of-band actions

Not achievable via a file change in this repository, and not attempted here:

- **The `release` branch has no required status checks** in its branch protection today (`docs/handoffs/FASTI_BRANCH_TOPOLOGY_CHANGE_2026-08-24.md`). Worth fixing alongside the Environment setup below, for the same reason.
- **The `production-release` GitHub Environment and its required reviewers** must be created by a maintainer with admin rights (Settings → Environments → New environment). Until it exists, the `publish` placeholder job in `release.yml` runs unprotected like any other job.
- **B8a's own evidence formalization** (a `create_b8a_milestone_manifest` proving native/OCI/source-build/rollback/hardware-budget evidence the same way B1's manifest proves its own gates) is a separate, prerequisite body. B8b's `xtask` wiring only adds the `Body::B8a` enum variant and a deliberate `bail!` stub for its `run_milestone` arm, so B8b's own fail-closed check against a B8a manifest is meaningful once that work happens.
